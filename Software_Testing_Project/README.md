# Software Testing Project — Cargo Delivery Program

**Seneca Polytechnic · SFT221 Software Testing · 6인 팀 프로젝트 (2023년 6~8월)**

교수님이 제공한 **C 언어 화물 배송 프로그램**을 대상으로 요구사항을 분석하고, 테스트 계획 수립부터 함수 명세·Unit Test·Integration Test·결과 문서화까지 진행한 수업 팀 프로젝트입니다.

> **기여 범위:** 배송 프로그램 전체를 혼자 개발한 프로젝트가 아닙니다. 본인의 테스트 계획 문서 일부, 함수 명세 정리, 좌표 변환 관련 테스트 설계·코드 작성 및 보고서 작업을 중심으로 소개합니다. 결과 수치는 **팀의 제출 보고서에 기록된 값**이며, 이 README를 작성하면서 테스트를 새로 실행한 값은 아닙니다.

## 테스트 대상: 화물 배송 프로그램

입력된 화물의 **무게, 부피, 목적지**와 트럭별 경로·적재 조건을 고려해 배송 차량을 결정하는 프로그램입니다. 지도·경로 처리와 배송 로직이 연결되어 있어 개별 함수만이 아니라 함수 간 데이터 전달도 검증해야 했습니다.

- 입력 유효성 및 배송 정보 처리
- 목적지 좌표 변환 (`convertStrToPoint`, `convertPointToStr`)
- 지도/경로 구성 및 배송 경로 연산
- 적재 제약과 트럭 배정 로직

| **보고·협업** | Excel 테스트 문서, Visual Studio 테스트 코드 및 Scrum 결과 정리, GitHub·Jira 활용 |

## 1. Test Plan: 무엇을, 어떤 기준으로 검사할 것인가

테스트 수행 전 계획서의 세 영역을 맡아 정리했습니다.

- **Control Procedures:** 테스트 결과 검토, 변경·이슈 처리 절차, 진행 일정과 검증 활동의 관리 방식
- **Resources and Responsibilities:** 프로젝트 참여자의 역할과 테스트 담당 업무 구분
- **Tools:** 버전 관리와 이슈·협업에 사용할 도구 및 테스트 환경 정리

**배운 점:** 테스트 결과가 남더라도 누가 어떤 기준으로 수행했는지 설명할 수 없다면 재현하거나 협업하기 어렵습니다. 테스트 계획서는 단순한 형식 문서가 아니라 **검증 기준과 책임 범위를 맞추는 수단**이었습니다.

## 2. Unit Test: 함수 하나의 입력과 출력을 검증

테스트 대상 함수 중 하나인 `convertStrToPoint`는 `"3B"`처럼 표시된 좌표 문자열을 내부 `Point` 구조체로 변환합니다.

```c
// 검증 대상 함수의 형태
struct Point convertStrToPoint(const char* dest);
```

주요 확인 조건:

- **정상 입력:** 예를 들어 `"3B"`, `"1A"` 등의 좌표 변환 결과
- **경계값:** 지도 범위 시작·끝, 숫자 자릿수, 대소문자 입력
- **비정상 입력:** 음수, 잘못된 문자, 공백, 예상 범위를 벗어난 좌표 등
- **테스트 설계 관점:** 기능 요구사항에 따른 Black-box 케이스와 코드 경로를 고려한 White-box 케이스

Visual Studio의 C++ Unit Test 코드에서 `Assert::AreEqual()` 등을 이용해 기대 결과와 실제 결과를 비교했습니다.

**주의:** 비정상 입력은 반드시 정상 결과가 나왔다는 뜻이 아닙니다. 실패한 사례도 테스트 결과로 기록해, 어떤 조건에서 예상과 다르게 동작하는지 드러내는 것이 목적이었습니다.

## 3. Integration Test 2: 함수 사이의 연결 검증

Unit Test가 함수 하나의 동작을 확인했다면, Integration Test에서는 여러 함수의 입력·반환값이 **서로 호환되는지** 확인했습니다.

```text
좌표 문자열 입력
      ↓
convertStrToPoint()
      ↓
Point 구조체
      ↓
convertPointToStr()
      ↓
다시 문자열로 변환된 값 비교
```

- Excel에 테스트 입력, 기대 결과, 실제 결과 및 Pass/Fail 기록
- Visual Studio에서 관련 테스트 코드 작성
- 양쪽 변환 함수의 결과가 연속 처리 과정에서 유지되는지 확인
- 최종 **Integration Test 2 보고서의 16개 테스트 사례가 모두 Pass**로 기재됨

위의 `16개 Pass`는 **당시 제출 보고서의 결과**입니다. Unit Test 결과 중 실패 사례가 있다는 점과 구별해 기록했습니다.

## 4. 테스트 중 어려웠던 점과 AI 활용

테스트 코드에서 오류 메시지가 발생하거나 예상 결과와 실제 결과가 다르면, 단순히 Pass/Fail만 확인해서는 원인을 이해하기 어려웠습니다. 생성형 AI를 **오류 메시지·실행 흐름·경계 조건을 이해하는 보조 도구**로 활용했습니다.

1. 문제가 발생한 함수, 입력 조건, 기대 결과를 구분했습니다.
2. AI의 설명으로 관련 코드의 동작과 가능한 원인을 학습했습니다.
3. 제안 내용을 그대로 결론으로 사용하지 않고 소스코드·요구사항·실행 결과와 대조했습니다.
4. 확인된 결과를 테스트 문서에 기록했습니다.

이 경험을 통해 **AI는 분석을 도울 수 있지만, 무엇이 올바른 결과인지 결정하고 재현·검증하는 책임은 개발자에게 있다**는 점을 배웠습니다.
